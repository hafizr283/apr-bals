# Numerical hypothesis and measurement boundaries

The reviewer suggests that roughly 187,512 scalar atomic additions might give a worst-case FP32 accumulation bound of order 1e-2. The actual scalar kernel does not atomically add every rating. In `fused_kernels.cuh`, each thread first accumulates a segment into `l_v`, adds the segment to its job accumulator `lhs_vals`, and atomically flushes that accumulator once per job. Jobs visit strided nonempty tiles, with at most eight tiles per job by construction.

For a unique user-item matrix, each tile segment has at most YB observations (256 at K<=32, 128 above). If J jobs contribute to an entity's tile row, a conservative componentwise absolute bound has the form

    |Ghat - G| <= [(1+gamma_YB)(1+gamma_8)(1+gamma_J)-1] * |F|^T |F|,
    gamma_n = n*u/(1-n*u), u = 2^-24.

This is a hierarchical sum bound, not gamma_degree. J depends on the number of occupied column tiles in the tile row (including other entities in that tile row). Cancellation can make relative entrywise errors arbitrarily large, so the probe reports upper-triangle relative Frobenius error and maximum absolute error normalized by maximum reference magnitude instead.

The FP64 experiment invokes the actual atomic, FP16 dense, FP32 same-dataflow, and FP16 giant kernels on identical trained FP32 factors. It does not compare Grams from independently trained models: those differ for reasons beyond arithmetic. The FP16-rounded FP64 Gram additionally separates operand rounding from accumulation error. Each selected entity retains its entire original 32-row tile neighborhood in the probe, preserving the occupied column tiles and job/partial-sum grouping of the atomic path. Only the requested top-20 entities per side are scored. All matrices are unregularized; only the upper triangle consumed by the solvers is compared.

A negative result must be retained: if FP32 has smaller Gram error and the two FP32 training paths agree, then the atomic-error explanation is not supported. A slight train/test advantage for rounded operands does not imply more accurate Gram construction. It can arise from a perturbed optimization trajectory, because the gathered factors used in both Gram and RHS are rounded. Establishing the precise cause requires further controlled perturbations rather than asserting “implicit regularization.”

Timing boundary: the original `justapr` per-phase CUDA events execute on the default stream, which joins the compute and solve streams. Consequently the reported LHS+RHS interval can include overlapped solve time, while the following solver interval is almost zero. These are compute-phase timings, not isolated kernel timings. Training-loop wall time remains a usable comparison. New time-to-target curves record cumulative elapsed time at each evaluated sweep instead of multiplying sweep count by a mean sweep time.

The manuscript also states that TF32 has eight more mantissa bits than FP16. That is incorrect for Ampere TF32: both have 10 stored fraction bits; TF32 has the wider FP32 exponent range. FP32 has 23 stored fraction bits. Consequently, TF32 versus FP16 is not a full-precision-versus-half-precision test. Source: [NVIDIA's Ampere TF32 description](https://developer.nvidia.com/blog/accelerating-ai-training-with-tf32-tensor-cores/). The same-dataflow FP32 leg is essential to the requested isolation.

Register audit of the new FP32 control: the fully unrolled rank-96 FMA loop used 255 registers and spilled (144 B stores / 96 B loads). Disabling contraction-loop unrolling at K=96 reduced it to 236 registers with zero spills. Lower ranks retain unrolling and use 95/114/136/178 registers, zero spills. The primary rank-96 control is built with the spill-free loop, before its measurements start. Static comparison is saved in `logs/build_sameflow_k96_unroll1.txt` and the earlier build logs. No speedup should be attributed to an avoidably spilling control.

Final K96 control tuning: four zero-spill loop variants were timed on ML20M without using accuracy for selection. The outer-contraction loop won (7.22289 s versus 17.44501 s for unroll1, 10.81761 s for unroll4, and 10.75069 s for unroll8). It uses 254 registers with zero spill loads/stores. The initial K96 comparison logs are preserved in `control_tuning_initial/`; primary `four_way/` K96 logs are replaced with the selected control. Lower-rank controls are unchanged.

Accumulator diagnostic: `chunked_src/` changes only the dense FP16 path's accumulation: compute each 16-row chunk into a zeroed MMA fragment, then add it to the persistent fragment with FP32 CUDA-core additions. Operand rounding, tile order, RHS construction, solver, and training budget are retained. Compare its full trajectories and same-factor Gram outputs with the original persistent-MMA path and rounded-FMA control. This is a mechanism experiment, not a new speedup headline. NVIDIA's [PTX specification](https://docs.nvidia.com/cuda/archive/11.5.1/parallel-thread-execution/index.html) does not specify the accumulation order, rounding, or subnormal handling for these matrix instructions; do not equate an FP32 accumulator type with a guaranteed sequence of IEEE round-to-nearest scalar FMAs. Any measured bias here is a result for this GPU/kernel, not a portable hardware guarantee.

Completed original-path probe (800 entity snapshots per path across 4 datasets x 5 ranks x 2 sides x 20 entities): median / maximum relative upper-triangle Gram errors are atomic FP32 1.23e-7 / 3.41e-7, same-dataflow FP32 2.01e-6 / 9.26e-6, dense FP16 1.86e-4 / 2.05e-3, and giant FP16 4.55e-5 / 5.07e-4. Median relative trace biases are approximately -6.3e-10, -5.2e-7, -2.16e-4, and -5.01e-5 respectively. These measurements reject the proposed explanation that atomic FP32 is the less accurate Gram path. The tensor paths' downward bias and the accumulation-reset experiment should be discussed separately from their recommendation accuracy.

Completed accumulation intervention: all 20 chunk-reset training runs return test RMSE to within 2e-6 of the same-dataflow FP32 control. Across the same 800 heavy-entity snapshots, resetting each 16-row MMA reduces median/max relative Gram error to 4.05e-6/1.38e-5 and median relative trace bias to -2.18e-8, versus dense persistent MMA's 1.86e-4/2.05e-3 error and -2.16e-4 trace bias. The rounded-FMA control and chunk-reset tensor control both remain near the full-FP32 training outcome. Thus the original slight train/test advantage is a changed optimization trajectory caused by persistent tensor accumulation in this implementation, rather than more accurate Grams or FP16 operand rounding alone. The FP32 atomic-error hypothesis is rejected. The observation is not a general claim that biased accumulation improves recommendation accuracy.

Suggested manuscript wording: “FP64 reference checks on the twenty highest-degree users and items show that the FP32 atomic baseline has lower Gram error than the tensor paths. The dense tensor path instead exhibits a small downward Gram bias. Holding rounded operands and the solver fixed, resetting the MMA accumulator every sixteen observations and combining chunks with FP32 scalar additions removes this bias and restores the FP32 RMSE trajectory (maximum final test-RMSE difference 2e-6 over twenty dataset/rank settings). The small accuracy shift therefore originates in persistent tensor accumulation, not in superior Gram accuracy or atomic-add error.” These controls use the original split; report new-split accuracy differences separately from `validation_accuracy_pair.csv`.

BF16 safety controls: all eight BF16 Gram+solver configurations (one refinement, beta .3/.5, four datasets) finish with zero non-finite guards. Twelve additional FP16 controls on GPU0 show that beta .5 is already stable on all three MovieLens datasets, but fails on Netflix at lambda .048: FP16 with one refinement zeroes3,142 entity-solves and ends at test RMSE1.440298; shipped no-refinement FP16 zeroes3,492 and ends at1.339762. BF16 with one refinement at the same beta ends at0.817964 with zero guards. At beta .3, matched Netflix FP16/BF16 RMSE is0.817803/0.817821, so this is a range/safety result rather than a claim of uniformly better BF16 accuracy. Both Gram operand and solver tile types change in the BF16 configuration; these runs do not isolate which type change alone prevents failure. GPU0 control times must not be compared to GPU1 BF16 timing as a performance experiment. See `bf16_controls.csv` and `bf16_matched_comparison.csv`.

FP32 fallback follow-up: `fallback_src/` retains the original FP16 fast path but queues failed entity solves for the validated tiled FP32 solver. On the new split at Netflix K96, beta .5, lambda .048, both the no-refinement and one-refinement variants encounter two initial FP16 failures per 14,938,770 solves and recover both in FP32. Their median validation/test RMSE is .822030/.821171 and .822022/.821168, compared with .822022/.821168 for all-FP32. On the original split, the fallback prevents the zero-induced cascade: it recovers all 33 no-refinement failures and all 26-27 refined failures, ending at test RMSE .817962-.817964 and .817956-.817957. Matching zeroing controls accumulate 3,406-3,463 and 3,161-3,175 failures. No FP32 retry failed in the tested runs. This supports the checked fallback in these configurations; it does not turn the earlier BF16 comparison or this small test set into a universal precision-safety claim. See `FP32_FALLBACK_PROTOCOL.md`.
